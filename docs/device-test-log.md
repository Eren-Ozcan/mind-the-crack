### 5 bugs found and fixed

All five showed up **only on device** or only in the running game.

1. **`Can't add component because class 'CapsuleCollider' doesn't exist`**
   IL2CPP stripped the physics module (the game does not use physics), but
   `GameObject.CreatePrimitive` adds a collider. Fix: cube/quad meshes are
   generated by hand (`Greybox.cs`), the physics module never enters the
   build.

2. **`ArgumentNullException: Parameter name: shader`**
   `Shader.Find("Standard")` is null in the build. Since no material in the
   scene referenced them, the built-in shaders were stripped. Fix: our own
   shader `Assets/Resources/Greybox.shader`.

3. **The game never progressed (`0.0 m`).**
   `RunController.OnEnable` subscribed to the beat event, but `OnEnable`
   runs inside `AddComponent` — before Bootstrap assigns the `Conductor`.
   The subscription silently never happened. Moved to `Start`.

4. **`GUI.skin` null — HUD throws an exception every frame.**
   Engine code stripping also stripped the default GUI skin (same root
   cause as #2). Temporary fix: `PlayerSettings.stripEngineCode = false`.
   **Debt:** stripping will be re-enabled once the HUD becomes real UI and
   the scene is authored; right now it bloats the APK.

5. **The lines were invisible.**
   Every slab was a separate raised cube and the line was the gap between
   them. At a 29° camera angle the 0.26 height of the slab in front fully
   hid the 0.13 gap. Enlarging the gap was the wrong fix: a single-piece
   sidewalk strip + dark lines painted on top. Readable from any angle.

### Tuned

Character height 1.1 → 0.75 (it was covering the two slabs in front of it —
exactly the area that has to be read), camera 3.4/-4.2 → 3.9/-4.6, FOV
55 → 46, tilt 29° → 31°, preview markers made thinner.

### Not measurable

- **Audio latency.** `adb shell input tap` latency is 100–300 ms and
  variable; the on-screen offset reflects adb's latency, not the device's
  audio latency. The real measurement must be done by hand (`test-plan.md`
  §3 protocol).
- **Is it fun.** That is the Phase 0 gate and it needs humans.
- **Long session behaviour** (thermal throttling, sync drift) — not visible
  in 20 second rounds.

### Next

1. Play by hand: does the offset keep drifting in the same direction? (the
   first sign that calibration is needed)
2. 10 person playability session — gate: ≥6 people must not put it down for
   5 minutes.

## 2026-09-22 — Second round: screen recording

Same device. 12–14 s recording with scrcpy, frame-by-frame review with
ffmpeg. (The device has no `screenrecord` — Huawei removed it; captured with
scrcpy.)

### Found: the game was playing itself

The recording showed **1015.5 m → 1027.5 m**, score 1662 → 1683. So the game
had been alive and scoring for ten minutes without a single touch. Even
though the difficulty curve maxes out at 400 metres, a constant 1.0 step
survived.

Cause: reverse generation guarantees **solvability** but not
**necessity**. Filler slabs in wide gaps were laid out at ~1.0 intervals,
and a player doing nothing drifted along on top of them.

Fix and validation: `game-design.md` §3.2.

### The second problem this exposed

After the fix the game started killing from the very first step — the
difficulty curve started at 0 metres, so 20% of the first steps already
required a long step. `onboarding.md` §2, on the other hand, requires the
first seconds to be unlosable. The first 8 metres were made 100% normal
steps.

### Validation results

| Check | Before | After |
| --- | --- | --- |
| Intended path is safe | ✅ | ✅ 3.5M steps, 0 violations |
| Perfect is reachable | ✅ | ✅ |
| A player doing nothing dies | ❌ never died | ✅ 13 steps on average |

8 of the 13 steps are the safe opening. The threshold is 15 — **the margin
is thin**. Extending the safe opening would fail the test; this is
deliberate.

### Final state

On device `3.0 m, streak 3, PERFECT` — consecutive Perfects in the safe
opening, the preview shows the normal step in white and long/jump in red.
No Unity errors.
